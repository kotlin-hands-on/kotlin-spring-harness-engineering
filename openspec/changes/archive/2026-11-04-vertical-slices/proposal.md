# Proposal

## Why

The backend currently keeps its Exposed tables in a horizontal `persistence` package that every feature reaches into; the group and member features are flat packages with no internal layering. The user wants vertical slices with sub-horizontal layers instead: each feature owns its controller, domain machinery and persistence behind a small public facade, so features stop sharing a structural dumping ground and the boundary of every slice is explicit and enforced. This is the moment to fix it: eleven queued changes add slices (expenses, balances, settlements, ledger, …), and whatever layout they copy is the layout the codebase keeps.

## What Changes

- **New backend package anatomy (the canonical slice pattern, ADR `vertical-slices`)** — five parts, refined at the approval gate from the user's expanded answer:
  - **root package**: the slice's public API — one or *very few* services (the root follows the Single Responsibility Principle, so a domain whose public API spans genuinely different aspects may get more than one root service) plus the public value and sealed-result types that cross the slice boundary;
  - **`api/`**: the `@RestController` and HTTP mapping only;
  - **`domain/`**: non-service machinery — pure logic, POKOs, type hierarchies — that is internal to the slice (the public vocabulary root services hand out stays in the root);
  - **`application/`** *(optional, not created for group/member in this change)*: internal services that exist to keep root services focused by taking delegated work; callable only by the slice's own root services — never cross-slice, never from `api/`, `domain/`, `persistence/`;
  - **`persistence/`**: the slice's Exposed tables **and repositories**. Repositories are the only query surface: root and application services never touch the Exposed DSL or table objects directly.
  The `persistence` top-level package is dissolved: the `Groups` table and a new `GroupRepository` move to `group/persistence/`, the `Members` table and a new `MemberRepository` to `member/persistence/`; the query code currently inline in `GroupService`/`MemberService` migrates into those repositories.
- **Public API of a slice = its root package.** Cross-slice code (and the shared web/money zones) may reference only another slice's root types; `api/`, `domain/`, `application/`, `persistence/` are internal to the slice — with one sanctioned exception decided at the gate: **cross-slice table→table schema references** (FK definitions such as `Members.groupId references Groups.id`) are legal; cross-slice *query/DSL* access to another slice's tables is not, and needing it is a documented smell that the domains may be split incorrectly (the user, never the agent, decides whether a refactor is granted). Enforced by ArchUnit rules in `ArchitectureTest` (no Gradle module split), plus a frozen allowlist of shared top-level packages: the application root package, `web`, `money` (and the `:shared` module's wire contract). New top-level packages are new slices and must follow the anatomy, or the ADR is amended.
- **Shared group-token resolution (user decision D-4)**: a web-level `HandlerMethodArgumentResolver` resolves the `{token}` path segment to a verified `ResolvedGroup` by calling a new group root service method `GroupService.resolve(token): ResolvedGroup?` (repository-backed; replaces `byToken`/`GroupLookup` — see next bullet); both the group's own controller and the member controller receive the resolved context and never touch raw tokens. Token-less routes (`POST /api/v1/groups`) are unaffected because they declare no resolved parameter.
- **Internal signature follow-ups (no wire change)**: `GroupService.read/rename` and all `MemberService` use cases take the resolved group instead of a token; `GroupService.byToken` and the `GroupLookup` sealed interface are deleted (the resolver and `GroupAccess` use `resolve`, whose null return makes the indistinguishable unknown/malformed-token case explicit); the now-unreachable `NotFound`/`GroupNotFound` variants are removed from the sealed results (`GroupRead`, `MemberList`, `AddMember.GroupNotFound`, the group-half of `UpdateMember`/`DeleteMember`); `GroupAccess` keeps its token-based signature for the test probe.
- **New ArchUnit rules** (each proven to bite, verify-then-revert): cross-slice access goes through the slice root, with table→table FK references as the only cross-slice sub-package exception; Exposed DSL **and Exposed `Table` subtypes** stay inside `persistence/` sub-packages; only a slice's `api/` may depend on `web`; controllers never touch `GroupToken`; `application/` classes are depended on only by their slice's root (checks zero classes until an `application/` package exists — proven to bite with a temporary one); the existing controller rule is extended to also forbid `domain/`.
- **First ADR**: full text drafted in `adr.md` inside this change; materialized as `docs/adr/0001-vertical-slices.md` (MADR format) once approved. No Flyway migration — table objects only move between packages, the DDL is untouched and byte-identical.

**BREAKING** (internal only): the removed sealed variants/interfaces and changed service signatures are compile-time breaking for backend-internal callers; the HTTP API, status codes, JSON envelopes and money format are unchanged. Two unpinned wire nuances are accepted at the gate (see Resolved questions).

## Capabilities

### New Capabilities

None. This is a pure structural refactor: no requirement-level behavior is added.

### Modified Capabilities

None. The change declares `skip_specs: true`.

**Rationale (per the propose rules):** all three specs (`api-conventions`, `group-access`, `group-members`) pin wire behavior — status codes, error codes, JSON envelopes, token indistinguishability, `seq` values. None of that changes: every existing black-box/contract test stays green unmodified, and every existing spec scenario still holds with its original WHEN/THEN. The two resolver nuances accepted at the gate (unknown-token message text on member PATCH/DELETE; resolution-before-validation precedence) are unpinned by tests and specs — each spec scenario individually still holds. The architecture/layout rules live as executable ArchUnit tests and as the ADR, not as behavior specs. Inventing a requirement to justify a delta would violate the no-invented-requirements rule.

## Impact

- **Backend production code** (`backend/src/main/kotlin/com/example/harnessengineeringspring/`): every file in `group/`, `member/`, `persistence/` moves or is adjusted; `persistence/` is deleted. New: `group/persistence/GroupRepository`, `member/persistence/MemberRepository` (with `MemberDeletion`, its scoped-deletion outcome), `member/domain/MemberRow` (row POKO between repository and service), `group/ResolvedGroup`, `web/GroupContextResolver` + its registration. Deleted: `GroupLookup`, `GroupService.byToken`, `GroupRead`, `MemberList`, the `GroupNotFound` variants. `money/`, `HarnessEngineeringSpringApplication.kt` unchanged.
- **Backend tests**: test tree mirrors the slice layout (`group/api/`, `group/domain/`, `group/persistence/`, `member/api/`, `member/persistence/`, `support/`); new `web/GroupContextResolverTest`; `ArchitectureTest` gains five rules and one rule is extended. All existing behavior tests stay green without assertion changes.
- **Database**: none. Flyway migrations in `backend/src/main/resources/db/migration/` remain byte-identical; no migration is added.
- **ADR / docs**: creates `docs/adr/` with the first ADR (`0001-vertical-slices.md`, MADR format, status proposed → accepted at the approval gate).
- **Queued changes impacted** (flagged, not edited here — they are proposals pending their own planning): `ledger-core` (its proposal references backend persistence wiring; its design must use the slice anatomy — tables + repositories in the ledger slice's `persistence/`; its `..ledger..` ArchUnit references still resolve), `expenses-equal-split`, `expenses-exact-split`, `expenses-multiple-payers`, `expenses-shares-percent`, `balances`, `settlements`, `suggested-transfers`, `expense-restore`, `activity-feed` (each adds a new slice and must copy the canonical anatomy — root services call repositories, never the DSL; an `application/` sub-package only when a root service needs it; amount-carrying controllers receive `ResolvedGroup` and call `GroupAccess` from the group root). `web-shell` is unaffected (frontend only).

## Resolved questions (answered at the gate)

1. **Wire nuances — accepted, as recommended.** The resolver-throws design is confirmed (no sealed `Verified/Unverified` variant): unknown/invalid tokens are rejected by the resolver with 404 `not_found` before any handler runs. Both nuances are accepted and recorded as consequences of ADR Decision 4: (a) unknown-group-token message text on member PATCH/DELETE becomes uniformly "no such group" (status 404 + error code `not_found` unchanged; no test pins message text); (b) token resolution precedes body validation, so unknown-token + invalid-body requests answer 404 rather than 400 (no spec scenario or test pins the combined case).
2. **Service shape — root service is the use-case orchestrator (no thin facade), expanded by the user into the five-part anatomy above.** Recorded interpretation alongside it: the public vocabulary types root services hand out stay in the root per D-2, while `domain/` holds internal-only POKOs, type hierarchies and pure logic; `application/` is optional and created only when a root service actually delegates work to it (not created for `group`/`member` here); repositories are the mandated query surface.
